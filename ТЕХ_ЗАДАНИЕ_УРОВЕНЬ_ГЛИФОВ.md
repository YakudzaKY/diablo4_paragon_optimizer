# ТЗ: Уровни глифов и усиление нод в радиусе

## 1. Цель

Добавить в оптимизатор поддержку реальных уровней глифов и эффектов, которые усиливают ноды внутри радиуса глифа.

После доработки оптимизатор должен:

- не использовать флаг `legendary_glyphs`;
- брать уровень каждого прокачанного глифа из профиля;
- считать радиус глифа по уровню так же, как в игре;
- учитывать усиление `normal`, `magic` и `rare` нод в радиусе глифа;
- учитывать это усиление и при выборе, куда поставить глиф, и при поиске маршрута/распределении очков.

## 2. Текущее состояние проекта

### 2.1. Профили

Сейчас профили в `profiles/*.json` содержат булевый флаг:

```json
"legendary_glyphs": true
```

Этот флаг не описывает реальное состояние билда. Он говорит только "использовать максимальный/легендарный радиус" или "использовать стартовый радиус" для всех глифов сразу.

### 2.2. Радиус глифов

В `native/optimizer_cli.cpp` сейчас есть:

- `Options::legendary_glyphs`;
- чтение `legendary_glyphs` из профиля;
- CLI-аргумент `--legendary-glyphs`;
- функция `glyph_radius(const Glyph& glyph, bool legendary_glyphs)`;
- `build_scoring_context(..., options.legendary_glyphs)`;
- поле `legendary_glyphs` в итоговом JSON.

Фактически радиус выбирается так:

- если `legendary_glyphs = true`, берется `glyph.radius["legendary"]`;
- иначе берется `glyph.radius["starting"]`.

Это недостаточно, потому что в игре у каждого глифа есть конкретный уровень.

### 2.3. Данные глифов

Нормализованные данные уже содержат нужную базу:

```json
"radius": {
  "starting": 3,
  "legendary": 5,
  "upgrade_levels": [25, 50],
  "source": "wowhead.paragonCalc.glyphs.startingSize+upgradeLevels"
}
```

В текущем датасете:

- 182 глифа;
- у всех `starting = 3`;
- у всех `upgrade_levels = [25, 50]`;
- у всех `legendary = 5`;
- `max_level = 100`;
- tooltip у всех текущих глифов содержит Legendary Upgrade на Level 50.

Вывод: код должен быть data-driven и считать радиус по `starting` + `upgrade_levels`, а не по hardcoded уровням и не по булевому флагу.

### 2.4. Текущая модель глифов в скоринге

Сейчас оптимизатор в основном учитывает эффекты вида:

```text
For every 5 Dexterity purchased within range...
Required (purchased in range): +25 Dexterity
```

Это реализовано через:

- `parse_glyph_requirement`;
- `parse_scaling_value_per_5`;
- `glyph_threshold_stat`;
- `infer_glyph_bonus_stat`;
- `evaluate_glyph`;
- `assign_glyphs`;
- `glyph_route_node_bonuses`.

Но эффекты вида:

```text
Grants +30.0% bonus to all Magic nodes within range.
Grants +25.0% bonus to all Rare nodes within range.
Grants +20.0% bonus to all Normal nodes within range.
```

сейчас не структурированы и не применяются к ценности нод.

В текущих данных найдено 56 таких глифов:

- 17 усиливают `magic` ноды;
- 30 усиливают `rare` ноды;
- 9 усиливают `normal` ноды.

Для друида такие глифы уже есть в данных: `earth_and_sky`, `fang_and_claw`, `outmatch`, `dominate`, `keeper`, `poise`, `protector`, `shapeshifter`, `headhunter`.

## 3. Новая схема профиля

### 3.1. Удаляем `legendary_glyphs`

Из актуальной схемы профиля удалить:

```json
"legendary_glyphs": true
```

Из документации и примеров также удалить `legendary_glyphs`.

Рекомендуемая совместимость на один переходный релиз:

- если старый профиль содержит `legendary_glyphs`, CLI не должен падать;
- поле игнорируется;
- в `warnings` добавляется сообщение, что `legendary_glyphs` deprecated и нужно использовать `glyph_levels`.

Если обратная совместимость не нужна, можно сразу сделать поле ошибкой. Но для текущих профилей безопаснее сначала поддержать мягкую миграцию.

### 3.2. Добавляем `glyph_levels`

В профиль добавить поле:

```json
"glyph_levels": {
  "tectonic": 51,
  "spirit": 51,
  "earth_and_sky": 51,
  "fang_and_claw": 51,
  "outmatch": 51
}
```

Правила:

- ключ - `glyph.id` из `data/normalized/glyphs/<class>/*.json`;
- значение - целый уровень глифа;
- допустимый диапазон - `1..glyph.max_level`;
- неизвестный id - ошибка валидации профиля;
- уровень ниже 1 или выше `max_level` - ошибка;
- если глиф не указан, его уровень считается `1`;
- если глиф имеет положительный вес в `weights.glyphs`, но отсутствует в `glyph_levels`, добавить warning.

### 3.3. Миграция текущих профилей

Во всех текущих профилях нужно:

1. Удалить `legendary_glyphs`.
2. Добавить `glyph_levels`.
3. Для глифов из текущего билда поставить уровень `51`.

Глифы текущего билда определяются по положительным значениям в соответствующем `weights/*.json`, блок `glyphs`.

Список миграции:

```text
profiles/druid.example.json:
  tectonic, spirit, earth_and_sky, fang_and_claw, outmatch

profiles/druid.json:
  tectonic, spirit, earth_and_sky, fang_and_claw, outmatch

profiles/paladin_balanced.json:
  spirit, control, exploit, turf

profiles/paladin_juggernaut_shield_bash.json:
  sentinel, exploit, turf, spirit, honed

profiles/spiritborn.json:
  spirit, menagerist, wildfire, turf, exploit

profiles/warlock_succubus_endgame_weights.json:
  abyssal, demonologist, eldritch_sight, mastermind, ichor_carapace
```

Пример после миграции:

```json
{
  "class": "druid",
  "points": 270,
  "weights": "../weights/druid.json",
  "glyph_levels": {
    "tectonic": 51,
    "spirit": 51,
    "earth_and_sky": 51,
    "fang_and_claw": 51,
    "outmatch": 51
  },
  "starting_stats": {
    "strength": 440,
    "intelligence": 461,
    "willpower": 2460,
    "dexterity": 460
  }
}
```

## 4. Расчет радиуса по уровню

### 4.1. Требуемая функция

Добавить функцию уровня модели:

```cpp
double glyph_radius_for_level(const Glyph& glyph, int level) {
    double radius = glyph.radius_starting;
    for (int upgrade_level : glyph.radius_upgrade_levels) {
        if (level >= upgrade_level) {
            radius += 1.0;
        }
    }
    return radius;
}
```

Это логика для текущих данных:

```text
level 1..24  -> radius 3
level 25..49 -> radius 4
level 50..100 -> radius 5
```

Важно:

- не hardcode'ить уровни `25` и `50` в C++;
- читать их из `glyph.radius.upgrade_levels`;
- сортировать `upgrade_levels` перед расчетом;
- уровень `51` для текущих профилей дает радиус `5`;
- `glyph.radius.legendary` можно оставить только как справочное/контрольное значение, но не как основной источник выбора радиуса.

### 4.2. Структуры данных

`Glyph` нужно расширить:

```cpp
struct Glyph {
    ...
    double radius_starting = 0.0;
    double radius_legendary = 0.0;
    std::vector<int> radius_upgrade_levels;
    int max_level = 100;
};
```

`Options` нужно расширить:

```cpp
struct Options {
    ...
    std::map<std::string, int> glyph_levels;
};
```

В `GlyphInfo` добавить:

```cpp
int level = 1;
bool legendary_unlocked = false;
```

`legendary_unlocked` считать по последнему upgrade level или по отдельному структурированному полю, если оно будет добавлено позже. Для текущих данных уровень `>= 50` означает, что легендарный апгрейд доступен, но само значение Legendary Bonus пока не парсится и не входит в scope этого ТЗ.

## 5. Структурирование эффекта усиления нод

### 5.1. Новое поле в нормализованных глифах

В нормализованный JSON глифа добавить поле:

```json
"node_bonus": {
  "node_type": "magic",
  "bonus_percent": 30.0,
  "multiplier": 0.30,
  "source": "bonus_text.en"
}
```

Для глифов без такого эффекта:

```json
"node_bonus": null
```

Поддерживаемые `node_type`:

- `normal`;
- `magic`;
- `rare`.

Парсер должен распознавать английский текст:

```text
Grants +X% bonus to all Normal nodes within range.
Grants +X% bonus to all Magic nodes within range.
Grants +X% bonus to all Rare nodes within range.
```

Русский текст можно использовать как fallback:

```text
Усиливает все стандартные/магические/редкие узлы в радиусе действия на +X%.
```

Основной источник для парсинга - `bonus_text.en`, потому что он уже используется для threshold/scaling.

### 5.2. Расчет усиленных статов ноды

Если выбранный глиф стоит в сокете, а выбранная нода находится в его радиусе и тип ноды совпадает с `node_bonus.node_type`, то ее числовые статы получают множитель:

```text
effective_value = raw_value * (1 + node_bonus.multiplier)
extra_value = raw_value * node_bonus.multiplier
```

Усиление применять к:

- `node.stats` для подходящих `normal`, `magic`, `rare` нод;
- `node.bonus_stats` для `rare` нод только если требования этой rare-ноды выполнены.

Усиление не применять к:

- `priority_for_type`;
- ручным `scheme`-весам досок;
- `glyph_socket`;
- route-only бонусам;
- текстовым Legendary Bonus глифа, пока они не распарсены отдельно.

### 5.3. Подтвержденное правило для `purchased within range`

In-game проверка подтвердила: если сам глиф усиливает подходящие attribute-ноды в радиусе, то усиленная часть тоже идет в зачет `purchased within range` для требования и scaling этого же глифа.

Следствие для реализации:

- сначала применить `node_bonus` к подходящим нодам в радиусе выбранного глифа;
- threshold/scaling глифа считать по effective purchased stats внутри радиуса, а не по raw stats;
- если глиф усиливает `magic` ноды на `+30%`, то magic-нода `+10 Willpower` должна давать `13 Willpower` для проверки `Required (purchased in range)`;
- raw totals все равно нужны для диагностики/output, но requirement/scaling должны использовать effective in-radius totals.

Важно не удваивать учет: `node_bonus` добавляет extra stats ноды один раз; затем эти effective stats используются и в итоговом score, и в расчете `purchased within range` для соответствующего глифа.

## 6. Изменения в финальном скоринге

### 6.1. Общий порядок расчета

Нужно заменить текущий прямой расчет `totals` на расчет effective stats с учетом назначенных глифов.

Предлагаемый порядок:

1. Собрать выбранные ноды.
2. Назначить глифы по сокетам через `assign_glyphs`.
3. Для каждого назначенного глифа вычислить radius по `glyph_level`.
4. Найти выбранные ноды в радиусе каждого глифа.
5. Применить `node_bonus` к подходящим нодам.
6. Посчитать raw totals и effective totals.
7. Проверить требования rare/legendary нод по effective totals.
8. Активировать `bonus_stats` только для нод с выполненными требованиями.
9. Если активированный `bonus_stats` принадлежит rare-ноде под `node_bonus`, усилить и `bonus_stats`.
10. Для каждого назначенного глифа пересчитать `stat_in_radius`, requirement и scaling по effective stats выбранных нод в радиусе.
11. Повторять шаги 6-10 до fixed point, если усиление атрибутов или включение `bonus_stats` открывает новые rare-бонусы либо requirement глифа.
12. Посчитать финальный score.

### 6.2. Что должно попасть в output

В JSON результата для каждого глифа добавить:

```json
{
  "glyph": "earth_and_sky",
  "level": 51,
  "radius": 5,
  "legendary_unlocked": true,
  "node_bonus": {
    "node_type": "magic",
    "bonus_percent": 30.0
  },
  "affected_nodes": [
    {
      "node": "...",
      "type": "magic",
      "raw_score": 12.0,
      "bonus_score": 3.6
    }
  ],
  "node_bonus_score": 123.45
}
```

`affected_nodes` можно ограничить top N или включать только при `--include-route-steps`, если полный список сильно раздувает JSON.

В корневом payload заменить:

```json
"legendary_glyphs": true
```

на:

```json
"glyph_levels": {
  "earth_and_sky": 51
}
```

## 7. Изменения в выборе глифа для сокета

`assign_glyphs` сейчас выбирает глифы по `evaluate_glyph`, где основной вклад идет от threshold/scaling и предпочтения `weights.glyphs`.

Нужно расширить `evaluate_glyph`:

- если у глифа есть `node_bonus`, посчитать дополнительный score от всех выбранных подходящих нод в радиусе этого сокета;
- этот score должен зависеть от весов статов в `weights.weights`;
- глиф с node bonus должен выигрывать на сокете, где в радиусе есть сильные подходящие ноды;
- requirement/scaling кандидата считать по effective stats в радиусе после применения его `node_bonus`, потому что in-game `purchased within range` учитывает усиленные attribute-ноды;
- если requirement глифа не выполнен, primary node bonus все равно должен работать, потому что Additional Bonus и primary эффект - разные части tooltip.

Формула для кандидата:

```text
evaluation.score =
  threshold_scaling_score
  + requirement_activation_score
  + preferred_glyph_score
  + node_bonus_score
```

`node_bonus_score`:

```text
sum(weighted_stats_score(node.stats, weights) * node_bonus.multiplier)
+ sum(weighted_stats_score(active_bonus_stats, weights) * node_bonus.multiplier)
```

Для первой версии можно считать `active_bonus_stats` по текущей модели требований. Если из-за усиления атрибутов rare-бонус активируется только после выбора глифа, финальный скор должен это увидеть через fixed point из раздела 6.

## 8. Изменения в маршрутной эвристике

### 8.1. Требование

Оптимизатор должен учитывать усиление нод не только после того, как маршрут уже построен, но и во время поиска маршрута.

Это важно для двух сценариев:

- "куда бы поставить глиф" - выбор сокета/доски должен учитывать, какие magic/rare/normal ноды реально усиливаются;
- "просто очки раскидать" - маршрут должен охотнее брать ноды в радиусе глифа, если они получают хороший bonus multiplier.

### 8.2. Расширение `glyph_route_node_bonuses`

В `build_glyph_value_matrices` / `glyph_route_node_bonuses` добавить вклад `node_bonus`.

Для каждой пары `(socket, glyph)`:

1. Взять radius по уровню конкретного глифа.
2. Найти ноды в радиусе.
3. Для каждой ноды подходящего типа посчитать marginal value:

```text
node_bonus_route_value =
  weighted_stats_score(node.stats, weights)
  * node_bonus.multiplier
  * glyph_route.node_bonus
```

4. Если нода rare и имеет потенциальные `bonus_stats`, добавить route hint:

```text
rare_bonus_hint =
  weighted_stats_score(node.bonus_stats, weights)
  * node_bonus.multiplier
  * RARE_BONUS_ROUTE_HINT_FACTOR
```

5. Ограничивать вклад через `max_bonus_multiplier`, как текущие glyph-route бонусы.

### 8.3. Новая настройка `glyph_route`

В `weights/*.json` добавить опциональный коэффициент:

```json
"glyph_route": {
  "node_bonus": 1.0
}
```

Значение по умолчанию:

```text
node_bonus = 1.0
```

Диапазон:

```text
0.0..10.0
```

Если `node_bonus = 0`, новая эвристика отключается, но финальный скор все равно обязан учитывать node bonus.

## 10. Тесты и проверки

### 10.1. Unit-тесты нормализации

Добавить тесты в `tests/test_crawler_parsing.py` или рядом:

- `Grants +30.0% bonus to all Magic nodes within range` -> `node_type=magic`, `bonus_percent=30.0`;

- `Grants +20.0% bonus to all Normal nodes within range` -> `node_type=normal`, `bonus_percent=20.0`;
- glyph без node bonus -> `node_bonus=null`.

### 10.2. Unit-тесты радиуса

Для текущих данных:

```text
level 1  -> 3
level 24 -> 3
level 25 -> 4
level 49 -> 4
level 50 -> 5
level 51 -> 5
level 100 -> 5
```

Также проверить, что функция работает data-driven на synthetic glyph с другими `upgrade_levels`.

### 10.3. Unit-тесты профиля

Проверить:

- `glyph_levels` читается из профиля;
- отсутствующий глиф получает уровень `1`;
- неизвестный glyph id дает ошибку;
- уровень `0` дает ошибку;
- уровень выше `max_level` дает ошибку;
- старый `legendary_glyphs` дает warning или ошибку согласно выбранной политике миграции.

### 10.4. Scoring-тесты

Создать маленький synthetic graph:

- один socket;
- одна magic-нода в радиусе с `damage=10`;
- glyph с `node_bonus.magic=30%`;
- `weights.damage=2`.

Ожидаемый дополнительный score:

```text
10 * 0.30 * 2 = 6
```

Дополнительно:

- нода вне радиуса не усиливается;
- нода неправильного типа не усиливается;
- радиус уровня `24` не достает дальнюю ноду, радиус уровня `25` достает;
- threshold/scaling глифа считаются по effective in-radius stats: например `35` raw Willpower должно выполнить requirement `40`, если `node_bonus` усиливает enough Willpower-ноды до `40+`;
- rare `bonus_stats` усиливаются только если requirements выполнены.

### 10.5. Regression-проверки

После реализации прогнать:

## 11. Критерии приемки

Задача считается выполненной, если:

- все профили используют `glyph_levels`, а не `legendary_glyphs`;
- текущие профили мигрированы с уровнем `51` у билдовых глифов;
- радиус глифа считается от уровня через `upgrade_levels`;
- уровень `51` на текущем датасете дает radius `5`;
- node bonus глифов парсится в структурированное поле;
- финальный score учитывает усиление подходящих нод в радиусе назначенного глифа;
- requirement/scaling глифа учитывает усиленные attribute-ноды в радиусе, если их усиливает `node_bonus` этого глифа;
- `assign_glyphs` выбирает сокет с учетом усиления magic/rare/normal нод;
- route search получает дополнительный hint для усиленных нод в радиусе;
- output показывает уровень, радиус и вклад node bonus;
- README и schema output обновлены.

## 12. Внешние ориентиры для проверки

- Wowhead Paragon Glyphs Guide подтверждает, что глифы усиливают ноды вокруг сокета, а радиус зависит от уровня глифа: https://www.wowhead.com/diablo-4/guide/gameplay/paragon-glyphs-leveling-upgrading
- Wowhead Glyph Radius Guide подтверждает, что радиус является игровой механикой, зависящей от уровня: https://www.wowhead.com/diablo-4/guide/gameplay/paragon-glyph-radius-stats-nodes
- Пример глифа с усилением Magic nodes: https://www.wowhead.com/diablo-4/paragon-glyph/amplify-1031006

Важное замечание: внешние гайды могут отставать или иметь конфликт с текущими данными. Для реализации в этом проекте источником истины должны быть нормализованные `startingSize` и `upgradeLevels` из `data/normalized/glyphs`, потому что они приходят из используемого проектом `paragonCalc` payload.
